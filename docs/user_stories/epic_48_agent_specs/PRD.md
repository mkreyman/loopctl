# Epic 48: Agent specs

## Why

The agent delivery loop is a workflow on the outside with agents inside: a code-driven stage
machine (detected → triaged → queued → implementing → CI → merged) that dispatches model
sessions to runners. Anthropic's "Building Effective Agents" (KB `e5a5d9f6`) names the same
patterns: prompt chaining with gates, parallelization (the triage trio), orchestrator-workers
(dispatcher plus runners, the orchestrator being code), evaluator-optimizer (review).

What the loop lacks is the abstraction. Each dispatch kind was built as its own module set: a
candidate query, a payload builder, a budget pair, a result event, gates, stage effects, a
ledger kind and a runner prompt. Every failure of the first live end-to-end ticket (2026-11-07,
HCB #3922) was in that per-kind glue, never in an agent's reasoning: the ticket filter, closed
issues, a missing `.loopctl/mode`. Adding a third agent today means a third copy of the glue.

Mark, 2026-11-07, on the recommendation to keep loopctl as the durable workflow engine and
refactor the kinds into specs with an eval set per spec: "I agree with your recommendations!
Let's do it!"

## The decision

**An agent spec is a compiled description of one dispatch kind**, held in a code registry in
loopctl (`lib/loopctl/agents/specs/`), never a tenant-writable row. A spec composes behaviour
from closed sets of code: candidate predicates, payload builders, validators, screens, effects
and stage transitions named by reference. Each spec picks one **archetype**, and the archetype,
not the spec, decides what the agent may do to custody state:

| archetype | claims a story | binds | its output reaches | today |
|---|---|---|---|---|
| `:judge` | no, echoes the claim epoch | `triage_dispatch_id` | control-only edges, applied by control | triage |
| `:build` | yes, mints a session dispatch | `implementer_dispatch_id` | runner-reportable edges and `session_ended` | implement |
| `:draft` | no | nothing | a stored artifact a human releases, no stage edge | new (US-48.9) |

`:assess` (a separate reviewer) is not built: review runs inside the implement session on the
pr route and inside chg-server on chg sources. It becomes an archetype when a repo needs a
loopctl-dispatched reviewer.

**Why a code registry and not data.** A spec's `outcomes` and `effects` decide which edges and
row writes a runner's message can drive. Writable by a key, a spec could aim an agent-producible
outcome at a claim or a human-only edge, so one principal would both produce and certify, which
is the failure the custody model exists to prevent (CLAUDE.md: custody identity is never an
injectable input). Every list a spec touches is also already compile-time and published to
runners: the ledger's kind CHECK, `RunnerContract.Kinds`, the triage outcome enum. A registry
test can hold them equal; a row cannot. Per-tenant data is limited to knobs that cannot move
authority (enabled, budgets, batch size, filters already on the intake source).

**The prompt stays on the runner.** A dispatch never carries prose (`RunnerDispatch`: "never a
prompt"). A spec names a runner template by `{id, version}`; the runner declares the templates
it holds on join and loopctl derives eligibility from the declaration (KB `8dff6636`), storing
nothing per runner.

## What stays code, whatever a spec says

- Archetype semantics: claiming, operator-key resolution, the `implementer_dispatch_id` and
  `triage_dispatch_id` bindings, `:triage_not_bound`.
- Every L4 custody gate (self-report, self-review, self-verify, lineage, chg-root refusals).
- The stage-machine table. A spec names transitions; a compile-time check refuses one that
  names an edge outside its archetype's allowed set.
- Untrusted-input handling: fencing, the rule that reporter text never rides a `story`
  dispatch, the injection screen on anything that becomes a row or reaches a person, audit
  reasons built from enums only.
- The contract's casts and byte limits, the runner's refuse-by-default allow-list and its
  containment argv, the ledger's kind CHECK (regenerated by migration), the kill switch.

Every step before US-48.9 ships with no behaviour change and an equivalence test.

## Defaults coded where only Mark holds the fact

Each is the reversible option and is named in the epic PR for Mark to overrule.

1. **Eval cases are synthetic.** Support tickets may contain PHI, so no real ticket text goes
   into a committed eval case. Overrule: allow de-identified real tickets.
2. **A reply draft is stored in loopctl and never sent.** It is a `reply_drafts` row (RLS,
   tenant-scoped) that a human reads and sends; nothing in loopctl sends it, because a reply
   goes out in Mark's name. Overrule: post it as a draft comment on the HCB ticket instead.
3. **The drafter takes tickets whose triage ended `reject` or `escalated`** with no draft yet.
   Overrule in the spec's candidate list.

## Not in this epic

- The dependency-advisory bumper. It is the real test of "a new agent is a new spec": the
  second spec of an existing archetype (`:build`) should need zero loopctl modules. It waits
  for an advisory intake source, and for Gate B entries on the repos it may touch.
- An `:assess` archetype, for the reason above.
